# 手工原稿产出指引（实验 6）

> 指导书要求"手动设计单元测试用例，使用 LLM 生成测试代码初稿，人工修正测试代码，开展代码审查和走查，提交审查意见和测试报告"。本目录放人先做的两样东西：测试用例设计表、代码审查的清单与原始意见。测试代码的初稿在 02，修正过程在 03。

## 顺序不能反

1. 先设计用例，再生成代码。用例表是 LLM 的输入，不是 LLM 的输出。表里写清"输入什么、期望什么、为什么想到这条"，LLM 只负责把每一行翻成 JUnit 或 vitest。
2. 先审查代码，再改代码。审查意见先落纸面，再决定改不改、谁改，改完补回归用例。
3. 走查放最后，走的是测试代码和修改：每条测试到底断言了什么？有没有"怎么写都过"的用例？

## 用例怎么设计

- 每个数字都要有上下两边：100 字符不记、101 记；499 不落版本、500 落；4 次不锁、5 次锁；截止那一刻不逾期、过 1 毫秒逾期。数字从 `application.yml` 的 `liuhen.*` 和验收标准表来，不从代码里抄。
- 判定条件多于两个的先画表再写用例。提交时的"有无登记 × 有无 AI 粘贴 × 是否勾承诺"是判定表，不是三条 if。
- 有状态的画状态迁移图。编辑器的 idle / dirty / saving / offline，每条边一个用例。
- 走查记录里说"不改"的设计决定，也要有用例钉住，不然下次有人顺手改了没人知道。
- 走查第 22、24 条是实验 5 欠的：随机往返加大文本与整篇替换、前端自动化测试。这两条放在最前面。
- 凡是"打到数据库才会报错"的输入，都写一条期望服务层拒绝的用例。这类用例首跑很可能失败，失败就是发现。

## 审查怎么开

交叉审查，不审自己的代码：杨子航审周浩然的（work、registration、declaration、timeline），周浩然审杨子航的（account、policy、security、evidence），袁飞翔和孟甲审丁浩然的前端，丁浩然审袁飞翔的测试代码，张家森对照文案与文档。每人拿清单，逐文件看，意见写到纸上再录入。严重度三档：阻塞（不改不能评审）、应改（本周改）、建议（记下来，实验 8 排）。

## 走查怎么开

袁飞翔讲测试代码，一类一类讲。每条用例问三句：断言的是真行为还是 mock 的返回值？输入是不是边界？这条失败会说明什么？然后周浩然、杨子航、丁浩然各讲自己修的问题，说清"改了什么、哪条用例证明改对了"。记录：张家森。
